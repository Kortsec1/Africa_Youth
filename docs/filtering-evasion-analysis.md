# SNI 기반 필터링 우회·회피 기법 분석

이 문서는 캡스톤디자인 연구 범위에서 SNI 기반 필터링이 왜 한계를 가지는지 정리하기 위한 자료다. 실제 차단 사이트 우회 도구, 범용 프록시, VPN, 터널링 프로그램, 외부 서비스 대상 실험 방법은 다루지 않는다.

## 분석 범위

다루는 내용:

- 현대 인터넷 검열 방식의 계층별 분류
- SNI 기반 정책이 의존하는 관찰 지점
- SNI가 없거나 신뢰하기 어려운 경우의 정책 한계
- ECH 같은 프로토콜 변화가 정책 구조에 주는 영향
- 과거에 논의된 우회·회피 계열 기법의 개념적 분류
- 로컬 테스트베드에서 안전하게 재현 가능한 한계 실험

다루지 않는 내용:

- 실제 인터넷 차단 우회 절차
- 공용 프록시 또는 VPN 구현
- 외부 상용 서비스로 트래픽을 우회시키는 방법
- 특정 검열 시스템을 회피하기 위한 설정값, 코드, 자동화
- 탐지 회피 목적의 트래픽 은닉 기법 구현

## SNI 기반 필터링의 기본 가정

인터넷 검열과 필터링은 DNS, IP, HTTP, TLS/SNI, QUIC, 애플리케이션 계층 등 여러 위치에서 이루어질 수 있다. 전체 분류와 기존 우회 기법의 개념적 비교는 [현대 인터넷 검열 방식과 우회 기법 개요](modern-censorship-and-circumvention-overview.md)에 정리한다. 이 문서는 그중 TLS/SNI 기반 정책에 초점을 맞춘다.

SNI 기반 정책은 다음 가정에 의존한다.

1. 클라이언트가 TLS ClientHello에 SNI를 포함한다.
2. SNI 값이 평문으로 관찰 가능하다.
3. SNI 값이 실제 접속 의도와 충분히 일치한다.
4. 정책 장비가 ClientHello를 정상적으로 파싱할 수 있다.
5. 대상 도메인 단위 정책만으로 충분하다.

이 가정 중 하나라도 약해지면 SNI 기반 정책의 정확도와 적용 가능성이 떨어진다.

## 우회·회피 계열 기법 분류

### 1. SNI 미제공

일부 TLS 연결은 SNI를 포함하지 않을 수 있다. 이 경우 정책 장비는 도메인을 식별하지 못하므로 기본 정책을 적용해야 한다.

정책 관점:

- 보수적 환경: SNI가 없으면 차단
- 허용 중심 환경: SNI가 없으면 허용
- 관찰 중심 환경: 별도 로그로 기록 후 후속 분석

이 프로젝트의 로컬 실험:

```bash
openssl s_client -connect 127.0.0.1:9443
```

예상 결과는 `configs/policy.yaml`의 `default_action`에 따라 달라진다. 기본 설정은 `block`이다.

### 2. 알 수 없는 SNI

정책 파일에 없는 SNI가 들어오면 명시적 allow/block 규칙을 적용할 수 없다.

이 프로젝트의 로컬 실험:

```bash
./scripts/test-unknown.sh
```

기본 설정에서는 `unknown.test`가 `default_action: block`에 의해 차단된다.

### 3. SNI와 실제 서비스 관계의 불일치

SNI는 클라이언트가 선언하는 서버 이름이다. SNI만으로 HTTP 요청 경로, HTTP Host 헤더, 애플리케이션 계층의 실제 의도까지 확인할 수는 없다. TLS를 복호화하지 않는 정책 장비는 이 차이를 직접 검증할 수 없다.

정책 관점:

- SNI 기반 정책은 도메인 단위 제어에는 단순하고 빠르다.
- URL 경로, 본문, 로그인 상태, API 호출 내용은 확인할 수 없다.
- 더 깊은 검사는 TLS 복호화나 엔드포인트 협조가 필요하며, 개인정보와 신뢰 모델 문제가 생긴다.

### 4. ECH 적용

ECH(Encrypted ClientHello)는 ClientHello의 민감한 확장 정보를 암호화해 관찰 가능한 SNI 정보를 줄이는 방향의 기술이다. ECH가 널리 적용되면 기존 SNI 기반 정책은 대상 도메인을 직접 확인하기 어려워진다.

정책 관점:

- 기존 SNI 기반 allow/block 정책의 정확도가 낮아질 수 있다.
- IP, DNS, 인증서, 트래픽 메타데이터 같은 다른 관찰 지점에 대한 의존이 커질 수 있다.
- 개인정보 보호와 네트워크 정책 적용 사이의 균형 문제가 중요해진다.

### 5. 과거의 도메인 프론팅 계열 논의

도메인 프론팅은 TLS 계층에서 보이는 이름과 애플리케이션 계층에서 처리되는 목적지가 달라질 수 있다는 점을 이용한 것으로 알려진 과거의 회피 계열 기법이다. 현재 많은 대형 서비스 제공자는 이를 제한하거나 비활성화했다.

이 프로젝트에서는 외부 서비스 대상 실험이나 재현 절차를 제공하지 않는다. 연구 보고서에서는 다음 관점만 정리한다.

- SNI 기반 정책이 애플리케이션 계층 정보를 보지 못한다는 한계
- 서비스 제공자 정책 변화에 따라 기법의 실효성이 달라진다는 점
- 네트워크 정책, 서비스 약관, 개인정보 보호의 충돌 가능성

## 로컬 테스트베드에서 가능한 안전 실험

| 실험 | 명령 | 목적 |
| --- | --- | --- |
| 허용 SNI | `./scripts/test-allowed.sh` | 명시적 allow 정책 확인 |
| 차단 SNI | `./scripts/test-blocked.sh` | 명시적 block 정책 확인 |
| 알 수 없는 SNI | `./scripts/test-unknown.sh` | 기본 정책 확인 |
| SNI 없음 | `openssl s_client -connect 127.0.0.1:9443` | SNI 부재 시 정책 확인 |
| 비정상 데이터 | pytest 통합 테스트 | ClientHello 파싱 실패 처리 확인 |

## 보고서 작성 관점

보고서에서는 우회 도구의 제작 방법보다 다음 질문에 집중한다.

- SNI 기반 필터링은 어떤 정보를 보고 판단하는가?
- SNI가 없거나 암호화되면 정책 결정은 어떻게 달라지는가?
- 기본 정책을 allow로 둘 때와 block으로 둘 때의 장단점은 무엇인가?
- TLS 복호화 없이 가능한 정책과 불가능한 정책의 경계는 어디인가?
- ECH 확산은 기존 네트워크 보안 장비의 설계에 어떤 변화를 요구하는가?

## 결론

SNI 기반 필터링은 구현이 단순하고 TLS를 복호화하지 않아도 도메인 단위 정책을 적용할 수 있다는 장점이 있다. 반면 SNI 부재, 알 수 없는 SNI, ECH, 애플리케이션 계층 정보 비가시성 때문에 정책 정확도에는 구조적 한계가 있다. 본 프로젝트는 이러한 한계를 폐쇄형 로컬 테스트베드에서 관찰하고 문서화하는 데 초점을 둔다.
