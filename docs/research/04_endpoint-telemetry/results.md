# Windows 사용자 행동 수집 실험 보고서

**프로젝트:** Windows 포렌식 아티팩트 기반 Shadow AI 사용 행위 탐지 및 분석
**담당:** 동훈 — Windows 실시간 사용자 행동 수집
**실험 정리 기준일:** 2026년 11월 2일
**저장소 게시 정리일:** 2026년 11월 3일
**현재 상태:** 기본 프로그램과 주요 실험은 완료. 일부 실험은 아직 하지 못함.

## 1. 연구 목표와 구현 결과

### 1.1 연구 목표

이번 프로젝트는 Windows에 남은 여러 기록을 연결해 AI 서비스 사용 전후에 어떤 행동이 있었는지 분석하는 것이다. 여기서 동훈 담당은 **사용자가 PC를 쓰는 동안 발생하는 변화를 바로 기록하는 프로그램**을 만드는 것이다.

예를 들어 다음 상황을 생각할 수 있다.

> 메모장에서 문장을 복사했다 → ChatGPT 화면으로 이동했다 → 문장을 붙여넣었다 → 전송했다.

이 행동은 하나처럼 보이지만, 프로그램이 확인해야 하는 단계는 서로 다르다. **복사를 감지했다고 붙여넣기나 전송까지 확인한 것은 아니다.** 각 단계에서 어떤 기록을 얻을 수 있는지 실험했다.

### 1.2 수집 프로그램의 기능

실험용 프로그램은 크게 세 가지를 기록한다. 이런 초기 실험 프로그램을 PoC라고 한다.

| 기록하는 것 | 쉬운 설명 | 기록만으로 알 수 없는 것 |
|---|---|---|
| 클립보드 변경 | 복사한 내용을 담는 임시 공간의 상태가 바뀌었는지 | 어떤 문장을 복사했는지, 어디에 붙여넣었는지 |
| 활성 창 전환 | 메모장이나 브라우저 등 맨 앞에 있는 창이 바뀌었는지 | 사용자가 실제로 화면을 읽었는지, 전송했는지 |
| 프로세스 시작·종료 | 프로그램이 실행되거나 끝났는지 | 프로그램 안에서 어떤 문서나 대화를 다뤘는지 |

기본 설정에서는 복사한 문장 자체를 저장하지 않는다. 필요할 때 창 제목을 기록하는 옵션은 사용했다. 기록 파일은 이벤트 하나를 한 줄씩 저장하는 JSONL 형식이다.

### 1.3 주요 검증 결과

**클립보드 변경, 창 전환, 프로그램 시작·종료를 기록하는 기본 동작을 확인했다. 하지만 이것만으로 AI에 내용을 붙여넣거나 전송했는지 자동으로 확정할 수는 없었다.**

그래서 웹 실험에 한해 Chrome 확장 기능을 추가했다. 확장 기능은 실제 붙여넣기 이벤트를 기록했다. 별도의 개발자 도구 실험에서는 합성 문장이 전송 요청에 들어 있는 화면도 확인했다. 이 결과들은 서로 다른 실험에서 얻은 것으로, 처음부터 끝까지 하나로 연결된 자동 탐지 시스템은 아니다.

### 1.5 PoC 소스코드와 구성

PoC 코드는 **Program.cs**에 들어 있다. 보고서만 작성한 것이 아니라 기존 초안을 수정하고 Windows에서 실행한 구현이 있다. 이번 문서 재검토에서는 소스 구조와 파일을 다시 확인했으며, 실행 차단 상태에서 새로 실행하거나 빌드하지는 않았다.

| 파일 | 역할 | 연결된 원래 과업 |
|---|---|---|
| [Program.cs](poc/windows-collector/Program.cs) | 클립보드·활성 창·프로세스를 받고 JSONL에 저장하는 C# 본체 | 2·4·5 |
| [RealtimeCollector.csproj](poc/windows-collector/RealtimeCollector.csproj) | .NET8·Windows Forms·System.Management8.0.0 설정 | 4 |
| [README.md](poc/windows-collector/README.md) | 준비 환경, 실행·종료, 결과 확인, 현재 차단 상태 안내 | 재실행 안내 산출물 |
| [검증상태.txt](requirements.md) | 과거 빌드·실행 성공과 현재 제약 요약 | 검증 상태 |
| [validation/process-etw-test.ps1](poc/windows-collector/validation/process-etw-test.ps1) | 별도 ETW 세션과 테스트 프로세스를 사용한 비교 실험 | 3·5 |
| [chrome-paste-poc/manifest.json](tools/chrome-paste-observer/manifest.json) 등 | 웹 ChatGPT 붙여넣기 추가 실험용 확장 기능 | 5의 보조 실험 |

**Program.cs의 내부 역할**

| 구성 | 쉬운 설명 | 주요 위치 |
|---|---|---|
| Program | 실행 시간·저장 위치·제목 옵션을 읽고 시작과 종료를 처리 | 12행부터 |
| EventLogWriter | 이벤트를 대기열에 넣고 파일에 한 줄씩 저장 | 73행부터 |
| Collector | Windows 알림을 등록하고 받은 이벤트를 해석 | 142행부터 |
| StartWatcher | 프로세스 시작·종료 이벤트 구독과 세션 연결 | 211행부터 |
| OnWinEvent | 전면 창·제목 이벤트 처리 | 279행부터 |
| ClipboardEvent | 형식 조회·재시도·상태 변경 확인 | 322행부터 |
| Native | Windows 기능을 C#에서 호출하기 위한 선언 | 413행부터 |

수집 흐름은 **Windows 알림 → Collector의 이벤트 처리 → EventLogWriter → JSONL 파일**이다. 원문을 상시 저장하는 기능, 파일 I/O 전용 수집, 네트워크 송신 수집은 본체에 없다. ETW는 별도 실험 스크립트이며 C# 본체에 통합된 ETW 수집기로 설명하면 안 된다.

기존 코드에서 보완한 부분은 다음과 같다.

1. 클립보드 접근 실패 시 최대5회 재시도하고 조회 실패를 빈 데이터와 구분했다.
2. 재시도 중 내용이 바뀌면 이전 복사 결과로 연결하지 않도록 상태 번호를 확인했다.
3. WMI 종료 이벤트의 SessionID0 때문에 제외되던 이벤트를 PID·이름 기반 후보로 연결했다.

수정 전 백업은 원본 작업 폴더에 로컬 보존되어 있다. 원본 작업 폴더의 실행 파일은 bin/Release/net8.0-windows/RealtimeCollector.exe에 있으나 실행 차단 기록이 있으므로, 파일 존재와 실행 가능은 구분한다.

### 1.6 수집 방법 비교와 선택 이유

| 방식 | 선택·조사 이유 | 실제 확인 | 한계 |
|---|---|---|---|
| Clipboard API | 내용 변화 알림과 형식 정보를 얻음 | 알림·조회·재시도 검증 | 붙여넣기·전송 증거는 아님 |
| WinEvent hook | 현재 전면 창 전환을 알림으로 받음 | 전환·제목 이벤트 수신 | URL 미수집, 탭 횟수 대조 미완료 |
| WMI Trace | C#에서 프로세스 시작·종료를 구독 | 관리자 테스트에서 성공 | 종료 세션값 문제, PID 재사용 한계 |
| Security 로그 | 시스템이 제공하는 감사 기록 검토 | 정책과 읽기 조건 확인 | 관련 감사 없음, 실제 이벤트 생성 대조 미수행 |
| ETW | WMI와 독립적으로 프로세스 사건 비교 | 동일 테스트 시작·종료 확인 | 관리자 조건, 해석 경고, 장기 성능 미검증 |

현재 연구 단계에서는 기본 행위 맥락을 기록하는 본체와 독립 비교 실험을 구성했다. 공급자 간 지연·CPU 부하를 동일 조건에서 비교하지 않았으므로 특정 방법이 가장 빠르거나 무손실이라고 결론 내리지 않는다.

## 2. 실험 방법과 관측 결과

### 2.1 실험 환경

- Windows 11 Pro 데스크톱에서 진행했다. 확인된 운영체제는 25H2, 빌드 26200.9711이며 모든 과거 실행의 세부 업데이트 버전까지 따로 기록한 것은 아니다.
- C#과 .NET 8을 사용했다. 수정한 프로그램은 빌드할 때 경고와 오류가 없었다. 빌드는 소스를 실행 가능한 형태로 만드는 과정이다.
- 메모장, 설치된 ChatGPT 앱, Chrome의 웹 ChatGPT를 사용했다. 앱과 Chrome의 정확한 버전은 기록하지 못했다.
- 실제 개인정보나 업무 자료 대신 실험용 문장을 사용했다.
- 사용자가 수행했다고 알려준 행동과 프로그램이 직접 기록한 내용을 구분했다. 수동 행동마다 정확한 시각을 따로 찍은 것은 아니다.
- 별도 Windows 가상 머신을 준비하다 보류했으며, 아래 결과는 VM 실험 결과가 아니다.

### 2.2 실험 1 — 반복 복사 감지와 조회 재시도

**방법:** 메모장에 세 줄을 준비하고, 각 줄을 복사했다.

처음에는 메모장 복사에 대응하는 변경 알림 세 건이 있었지만, 그중 두 건은 데이터 형식을 확인하지 못했다. 당시 클립보드 상태에 접근하려는 내부 작업이 실패한 것이다. **메모장 창이 닫혔다는 뜻도, 복사 알림이 사라졌다는 뜻도 아니다.**

프로그램이 잠깐 기다렸다가 다시 접근하도록 수정했다. 다른 내용으로 바뀌었으면 이전 복사의 정보처럼 연결하지 않도록 상태 번호도 확인했다.

**다시 실험:** 세 줄을 각각 두 번씩, 총 여섯 번 복사했다.

| 확인 항목 | 결과 |
|---|---|
| 변경 알림 | 6건 |
| 텍스트 형식 확인 | 6건 모두 성공 |
| 재시도가 도움 된 경우 | 5건은 첫 접근 실패 후 두 번째에 성공 |

**결론:** 이번 조건에서는 재시도 수정이 효과가 있었다. 다만 여섯 번 성공한 것만으로 모든 환경의 성공률이 100%라고 할 수는 없다. 최초 접근 실패의 정확한 원인은 확정하지 못했다.

### 2.3 실험 2 — 복사 1회와 붙여넣기 3회의 기록 비교

**방법:** 한 번 복사한 문장을 같은 메모장에 세 번 붙여넣는 절차를 안내했고, 사용자가 완료했다고 보고했다.

**결과:** 클립보드 변경 알림은 한 건이었다. 텍스트 형식 확인은 성공했다.

**결론:** 붙여넣기를 세 번 했다고 변경 알림도 세 번 생기는 것은 아니다. **클립보드 변경 횟수로 붙여넣기 횟수를 계산하면 안 된다.** 붙여넣은 문장과 각 조작 시각은 이 로그에서 직접 확인한 것이 아니다.

### 2.4 실험 3 — 설치된 ChatGPT 앱의 붙여넣기 구분 한계

두 조건을 비교했다. A와 B 모두 설치된 ChatGPT 앱을 사용했다.

| 조건 | 사용자가 수행한 행동 | Windows 수집기에서 확인한 흐름 |
|---|---|---|
| A | 복사 → ChatGPT로 이동 → 붙여넣지 않음 | 클립보드 변경 → ChatGPT 창 전환 |
| B | 복사 → ChatGPT로 이동 → 붙여넣고 미전송 | 클립보드 변경 → ChatGPT 창 전환 |

**결론:** 현재 정보만으로는 붙여넣기를 직접 구분할 수 없었다.

A에서는 클립보드 알림이 세 건, B에서는 한 건이었으며 B 후반에는 Copilot 관련 창 전환도 있었다. 실험 조건이 완전히 같지 않으므로, 이런 차이를 붙여넣기 판별 기준으로 사용하지 않았다.

### 2.5 실험 4 — Chrome 붙여넣기 이벤트와 대조군 비교

Chrome에서 웹 ChatGPT에만 적용되는 실험용 확장 기능을 사용했다. 복사 원문은 저장하지 않고 붙여넣기 이벤트의 시각과 대상 요소의 종류 등을 기록했다.

| 사용자 행동 | 붙여넣기 이벤트 수 |
|---|---:|
| ChatGPT 입력창에 붙여넣기 | 1건 |
| 입력창 클릭만 하고 미붙여넣기 | 0건 |

**결론:** 이번 두 실행에서는 사용자가 수행한 행동과 이벤트 수가 일치했다. Windows 수집기만 사용했을 때보다 웹 붙여넣기 여부를 더 직접적으로 관측했다.

다만 각 조건을 한 번씩 확인한 결과다. 웹페이지가 붙여넣기를 막을 수도 있으므로 이벤트만으로 내용이 실제 입력됐다고 보장할 수는 없다. 이번 입력창에 문장이 보였다는 것은 사용자 확인으로 보완했다. 이 확장은 설치된 ChatGPT 앱이나 다른 앱까지 관측하지 않는다.

### 2.6 실험 5 — 합성 문장의 네트워크 요청 포함 확인

사용자는 **일반 Chrome에서 F12로 개발자 도구를 열어** 네트워크 요청을 확인했다고 설명했다. 이 실험은 앞선 확장 기능 실험과 별개다.

| 실험 문장 | CLIP-NET-20261026-A7F39 |
| 요청 목적지 | https://chatgpt.com/backend-api/f/conversation |
| 요청 방식 | POST — 데이터를 보내는 요청 방식 |
| 보낸 데이터 | 사용자 메시지 부분에 실험 문장이 포함됨 |
| 응답 상태 | HTTP 200 OK — 해당 요청에 정상 응답이 표시됨 |

**결론:** 사용자가 같은 요청을 차례로 펼친 화면 흐름을 근거로, 합성 문장이 요청 본문에 포함되고 정상 응답이 표시되는 수동 사례를 확인했다.

주의할 점은 다음과 같다.

- 화면은 확보했지만 요청 전체를 저장한 원시 네트워크 파일은 확보하지 않았다.
- Windows 클립보드 원문부터 전송 내용까지 자동으로 비교한 것은 아니다.
- 서버 내부에서 어떻게 저장·사용했는지는 알 수 없다.
- 붙여넣기만 한 조건에서 검색 결과가 없었던 것은 ‘찾지 못했다’는 뜻이며 미전송을 증명하지 않는다.
- 사용 도구는 사용자 확인에 따라 Chrome으로 기록했다. 요청 내부의 app_surface=codex_browser라는 값도 화면에 있었지만, 이 값이 왜 표시됐는지는 확인하지 못했다.

### 2.7 실험 6 — 프로세스 시작·종료 수집 검증

WMI는 Windows 시스템 정보를 조회하거나 이벤트를 받는 방식이다. 이를 사용한 초기 코드에서는 프로그램 시작은 보였지만 종료가 빠졌다.

관리자 권한으로 별도 확인한 결과, 종료 이벤트의 세션 번호가 실제 시험 환경과 다르게 0으로 전달됐다. 기존 코드는 현재 사용자 세션 번호인 1만 받았기 때문에 이 이벤트를 제외했다.

종료 이벤트를 먼저 받은 다음, 현재 사용자 환경에서 관측한 프로그램 번호와 이름으로 연결하도록 수정했다. 프로그램 번호를 PID라고 한다. 다른 프로그램이 같은 번호를 재사용할 수 있으므로 연결 결과는 ‘후보’로 남겼다.

ETW라는 별도 Windows 추적 기능으로도 같은 테스트를 확인했다.

| 시험 | 결과 |
|---|---|
| 테스트 프로그램 | cmd.exe, PID 23868 |
| 수정 WMI 수집 | 시작·종료 모두 확인 |
| ETW 추적 | 같은 프로그램의 시작·종료 모두 확인 |
| 테스트 프로그램 종료 코드 | 0 |
| ETW가 보고한 손실 | 0건 |

**결론:** 이번 테스트에서는 종료 이벤트가 빠졌던 문제의 수정 효과를 확인했다. 모든 조건에서 누락이 없다는 뜻은 아니다. ETW 변환 과정에 일부 해석 경고가 있었지만, 테스트 프로그램의 시작·종료 정보는 실제로 읽어 확인했다.

### 2.8 실험 7 — 파일 작업 수행과 수집 공백 확인

실험 스크립트로 합성 파일을 만들고, 19바이트를 읽고, 내용을 추가한 다음 이름을 바꾸고 삭제했다. 각 작업이 끝난 뒤 별도의 정답 기록을 남겼다.

**결과:** 파일 작업은 수행됐지만 현재 수집기에는 해당 작업을 직접 나타내는 이벤트가 없었다.

**결론:** 현재 수집기에 파일 작업 전용 기능이 없다는 공백을 확인했다. 이것을 ‘파일 작업이 없었다’고 해석하면 안 된다. 메모장에서 문서를 열고 읽는 실제 사용자 실험과도 구분한다. 이후 추가 검증에서 별도 합성 파일의 메모장 열기·편집·저장은 수행했다. 다만 수집기는 실행하지 못했으므로 파일 이벤트 수집을 검증한 것은 아니다.

### 2.9 Windows 이벤트 로그와 ETW 활용 범위

| 방법 | 쉬운 설명 | 이번에 확인한 범위 |
|---|---|---|
| Windows 이벤트 로그 | Windows가 조건에 따라 남기는 기록 | 관리자 조회 시 프로세스 생성·종료·파일 시스템 감사가 꺼져 있었음. 관련 이벤트를 실제 생성하는 실험은 안 함 |
| ETW | 필요한 Windows 이벤트를 선택해 추적 | 프로세스 시작·종료 시험 성공. 파일 작업 추적은 안 함 |

파일 접근 이벤트는 관련 감사 설정과 파일·폴더의 감사 조건 등이 필요하다. 현재 설정에서 모든 파일 읽기가 자동 기록된다고 가정하지 않았다. 기록이 있더라도 ‘파일 읽기’와 ‘AI로 전송’은 다른 판단이다.

## 3. 결과 해석과 기술적 한계

### 3.1 확인한 사실과 확인하지 못한 사실

### 3.2 추가 실험의 제약과 미수행 항목

창 전환 5왕복과 브라우저 탭 전환 5회를 세어 비교하려고 했지만, Windows의 Smart App Control이 실험용 실행 파일을 차단했다. 차단 이벤트와 파일 식별값을 대조해 같은 파일임을 확인했다.

개인 PC의 보호 기능은 끄지 않았다. 별도 Windows 환경을 준비하다가 보류하고, 기존 증거와 한계를 정리하는 방향을 선택했다. 따라서 아래 항목은 완료로 표시하지 않았다.

- 창 전환 5왕복·탭 전환 5회의 횟수 비교
- 파일 이름 변경·삭제까지 포함한 GUI 전체 시나리오와 여러 로그를 연결한 통합 실험
- 장시간 실행, 빠른 연속 행동, CPU·메모리 부담과 누락률 측정
- 감사 이벤트 및 ETW 파일 작업의 실제 수집

기존 로그에 창 전환 기록이 있다는 사실과 정해진 횟수의 검증을 끝냈다는 것은 다르다.

### 3.3 요구사항 충족 수준과 완료 판정

**기본 프로그램 구현과 주요 기능 실험을 마친 단계로는 정리할 수 있다. 원래 계획한 모든 조건의 검증까지 끝난 것은 아니다.**

| 마무리 방법 | 장점 | 남는 점 |
|---|---|---|
| 지금 결과로 현 단계 보고 | 이미 확인한 결과와 한계를 전달 가능 | 미수행을 분명하게 표시해야 함 |
| 나중에 추가 실험 | 창·탭·파일·부하 검증 보완 가능 | 프로그램 실행이 허용되는 환경부터 준비해야 함 |

현재는 첫 번째 방법으로 정리한다. 해시로 내용 비교하기나 전송 요청 자동 추적하기 등 추가 개발은 원래 6개 과업 범위를 넘겨 진행하지 않는다.

### 3.4 인수인계의 실험별 완료 기준 재점검

원래 기준은 실험을 수행하거나 미수행 이유를 명시하는 것이었다. 미수행 이유를 기록하는 것은 문서 요건을 충족하는 방법이지만, 실험 자체의 완료를 뜻하지 않는다.

| 원래 ID | 요구한 실험 | 현재 판정과 근거 |
|---|---|---|
| C1 | 메모장 합성 텍스트 복사 | 수행. 알림·형식 조회 실제 로그 확보 |

**재점검 결론:** 원래 요구한 수정 소스·실행 안내·원시 로그·결과표·한계 문서는 존재한다. 주요 구현은 실제 실험으로 뒷받침되지만, 모든 실험 기준을 실제 수행으로 충족한 것은 아니다. 보고서에는 W1/W2/P3와 X1/X2의 부족한 범위를 명시한다. 문헌 조사와 기본 검증을 완료한 범위를 넘어 전체 과업100% 완료로 표시하지 않는다.

| 장기 성능·무손실 보장 | 불가, 미검증 |

### 4.2 보고서에 사용할 결론

> Windows에서 클립보드 상태 변경, 활성 창 전환, 프로그램 시작·종료를 기록하는 실험용 프로그램을 만들고 주요 동작을 확인했다. 복사 알림만으로 붙여넣기나 AI 전송을 판단할 수 없다는 한계도 확인했다. 웹에서는 별도 확장 기능으로 붙여넣기 이벤트를 관측했고, 수동 네트워크 실험에서 합성 문장이 요청에 포함되는 화면을 확인했다. 다만 창·탭 횟수 비교와 파일·전송 통합 실험 등은 완료하지 못했으므로, 이번 결과는 기본 구현과 주요 기능 실험을 마친 단계로 정리한다.

### 4.3 용어 정리

| 용어 | 뜻 |
|---|---|
| 클립보드 | 복사·잘라내기한 데이터를 임시로 담는 공간 |
| 활성 창 | 현재 맨 앞에서 사용자와 상호작용하는 창 |
| 프로세스·PID | 실행 중인 프로그램과 그 실행을 구분하는 번호 |
| 이벤트 | 상태 변경이나 동작이 발생했다는 알림·기록 |
| 로그 | 이벤트를 저장한 기록 파일 |
| WMI | Windows 시스템 정보와 이벤트를 조회하는 기능 |
| ETW | Windows에서 선택한 이벤트를 추적하는 기능 |
| 대조군 | 행동의 차이를 비교하려고 일부 행동을 하지 않은 조건 |
| PoC | 아이디어가 실제로 동작하는지 확인하는 초기 실험용 구현 |
| 해시 | 파일 등이 같은지 비교할 때 쓰는 식별값. 이 연구의 증거 보존에도 사용 |

### 4.4 코드와 공유용 증거

| 자료 | 위치 |
|---|---|
| C# 본체·실행 안내 | [Windows PoC](poc/windows-collector/README.md) |
| 원래 요구사항 대조 | [충족 여부](requirements.md) |
| 수집 구조와 수정사항 | [구현 설명](implementation.md) |
| 공유용 실험 증거·보존 원칙 | [증거 안내](evidence/README.md) |
| Chrome 보조 확장 | [확장 실행 안내](tools/chrome-paste-observer/README.md) |

원시 JSONL11개, ETL, 전체 화면, 개인 PC의 시스템 진단은 로컬에 보존했다. 저장소에는 선택한 필드만 남긴 실험 기록과 요약을 게시한다. 게시본은 원시 로그와 동일한 파일이 아니며, 로컬 내부 검증과 공개 검증 가능 범위를 구분한다. 실제 사용자 SID·장치명·절대경로·창 제목을 포함한 원시 자료는 게시하지 않았다. 공유용 자료의 변환 규칙과 해시는 증거 안내에 기록했다.
