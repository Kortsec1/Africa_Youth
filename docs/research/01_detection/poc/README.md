# Shadow AI 상관분석 PoC

## 1. 목적

가상 이벤트를 공통 구조로 표현하고 시간순으로 정렬한 뒤,
규칙 기반 상관분석에 사용할 수 있는지 검증한다.

규칙 R01~R05를 구현하고 가상 데이터로 실행했다.
코드 실행과 비교 실험 결과는 [상위 results.md](../results.md)에 기록한다.

## 2. 파일 구성

- sample_events.json: 공통 구조로 작성한 가상 이벤트
- analyze.py: 규칙 분석기
- test_analyze.py: 13개 시나리오 및 추가 검증
- output.json: 기본 샘플 실행 결과
- compare.py: 연결 조건별 비교 실험
- comparison_cases.json: 비교 시나리오 9개
- comparison_output.json: 비교 실험 출력
- RUN.md: 실행 방법
- rules.md: 탐지 규칙 5개, 검증 시나리오 및 판단 수준

## 3. 공통 이벤트 구조

| 필드 | 자료형 | 의미 |
|---|---|---|
| event_id | 문자열 | 데이터셋 내 고유 이벤트 ID |
| occurred_at | 문자열 | 발생 시각. 시간대가 포함된 ISO 8601 형식 |
| device_id | 문자열 | 이벤트 발생 장치 식별자 |
| user_id | 문자열 또는 null | 사용자 식별자. 알 수 없으면 null |
| process_entity_id | 문자열 또는 null | 프로세스 인스턴스 식별자. PID만을 의미하지 않음 |
| event_type | 문자열 | 정규화한 이벤트 유형 |
| source | 문자열 | 원본 수집원 구분 |
| source_ref | 문자열 | 원본 레코드를 추적할 참조값 |
| synthetic | 불리언 | 가상 데이터 여부 |
| attributes | 객체 | 이벤트 유형별 세부 정보 |

위 필드는 입력에 모두 포함한다.
알 수 없는 사용자·프로세스 식별자는 null로 표현한다.

source_ref는 실제 수집 시 원본 파일과 레코드를 추적하는 데 사용한다.
가상 데이터에서는 synthetic: 접두사로 가상 레코드임을 표시한다.

## 4. 초기 이벤트 유형

| event_type | 의미 | attributes |
|---|---|---|
| file_access | 수집원이 관찰한 파일 접근 | file_path, access_kind |
| ai_service_access | 수집원이 식별한 AI 서비스 접근 기록 | service_id, domain, observation_kind |

file_access의 access_kind는 실제 수집원이 확인한 범위만 기록한다.
일반적인 파일 열기 기록을 임의로 read_data로 변환하지 않는다.

ai_service_access는 정규화한 분류명이다.
DNS 질의나 방문 기록 등 원본 관찰의 차이는 observation_kind로 보존한다.
이 유형 자체가 질문 전송이나 업로드를 의미하지 않는다.

파일 생성·Clipboard 변경 등 추가 유형은
탐지 규칙과 입력 요구사항을 정의하면서 확장한다.

## 5. 승인 정책과 이벤트의 분리

서비스 승인 상태는 이벤트에 고정해서 넣지 않고,
analyze.py의 POLICY 상수로 분리해 관리한다. 별도 정책 파일은 아직 구현하지 않았다.

정책에는 버전과 적용 시점을 기록하고,
분석 시 이벤트 발생 시각에 해당하는 정책을 적용한다.

승인 상태:
- approved: 정책에서 승인
- unapproved: 정책에서 명시적으로 미승인
- unknown: 적용할 정책 정보 부족

초기 정책은 서비스 단위의 가상 정책으로 단순화한다.
계정·테넌트·사용 목적에 따른 실제 조직 정책은 후속 확장 대상이다.

## 6. Timeline 처리 규칙

1. 가상 데이터 여부, 장치 ID, 시간대 및 ID 충돌을 검사한다. 전체 자료형 검증은 미구현이다.
2. 시간대가 없거나 해석할 수 없는 시각은 예외를 발생시켜 실행을 중단한다.
3. 시간대가 반영된 datetime으로 시각을 비교한다. 출력에는 원본 시각 표기를 보존한다.
4. 발생 시각 오름차순으로 정렬한다.
5. 시각이 같으면 event_id로 출력 순서를 고정한다.
6. 동일 시각의 출력 순서를 실제 행위의 선후관계로 해석하지 않는다.
7. 정렬 후에도 원본 event_id와 source_ref를 보존한다.

동일 event_id와 동일 내용이 반복되면 한 건만 사용한다. 중복 제거 건수는 별도로 출력하지 않는다.
같은 event_id에 서로 다른 내용이 있으면 입력 충돌로 처리한다.
서로 다른 ID의 유사한 이벤트는 임의로 삭제하지 않는다.

## 7. 상관분석 연결 원칙

- Timeline 정렬과 이벤트 연결은 별도 작업이다.
- 시간적으로 가깝다는 이유만으로 이벤트를 연결하지 않는다.
- 장치·사용자·프로세스 중 어떤 값을 필수로 비교할지는 규칙별로 지정한다.
- 필수 연결 키가 null이면 일치로 처리하지 않는다.
- 서로 다른 수집원의 사용자 식별자가 같은 체계인지 확인한다.
- 프로세스 식별자는 수집원 간 동일 인스턴스임이 확인될 때만 비교한다.
- 원본에 없는 식별자를 추정하여 관찰된 값처럼 저장하지 않는다.

## 8. 샘플 데이터 설명

sample_events.json의 이벤트는 모두 직접 작성한 가상 데이터다.
실제 Windows 로그나 브라우저 DB에서 추출한 기록이 아니다.

도메인은 예시용 ai.example.com을 사용한다.
실제 AI 서비스를 식별하는 도메인 목록이 아니다.

포함한 상황:
- PC-A의 USER-01: 파일 접근 이후 AI 서비스 방문 기록
- PC-B의 USER-02: 같은 시간대의 별도 AI 서비스 방문 기록
- PC-A의 사용자 미확인 방문 기록

입력 순서는 의도적으로 시간순과 다르게 작성했다.

Timeline의 예상 출력 순서:
evt-001 → evt-002 → evt-003 → evt-004

이 순서는 Codex 환경에서 코드를 실행해 확인했다.
R01 3건, R02 1건, R05 1건이 출력되며 동일 이벤트가 여러 규칙에 포함될 수 있다.

파일 접근과 서비스 방문의 연결 조건은 R02에서 평가한다.
이 샘플로 파일 업로드 여부를 확인할 수는 없다.
